## 1. E4：真实中文文献的 GB/T 7714-2025 格式检查

### 1.1 目的

回答两个问题：

1. 规则引擎在**真实中文文献**上能否稳定识别文献类型码、判全必填字段（即"检查器本身是否可用"）？
2. 对**典型格式漂移**，规则层到底能检出多少（即"检查器的能力边界在哪里"）？

### 1.2 方法

1. **取数**：OpenAlex `filter=language:zh,has_doi:true`，先复用 CiteBench-CN 构建时缓存的 16 页 / 3200 条作品池（`data/citebench_cn/openalex_zh_works.json`，CC0），再新抓 2 页 × 50 条（页 JSON 缓存在 `data/experiments/cache_e4/`，复跑 0 请求）。合并去重后 3183 条，按"题名含中文、有 DOI、有年份/来源、来源非索引库"筛出可用 2440 条，固定 `seed=20261022` 抽样 **100 条**。
2. **渲染**：按 `type` 映射为 GB/T 风格条目——`article/review → [J]`，`book/book-chapter → [M]`（`conference-paper → [C]` 的候选记录全部为英文题名，未进入可用集，故 C 组为 0）。页码用 en dash（`1–5`）作为"规范写法"。
3. **解析 + 检查**：`citeguard.reference_parser.parse_reference` 回解析，`citeguard.gbt7714.check_reference` 出问题清单。
4. **指标**：
   - **类型码识别率** = 回解析出的类型码与渲染类型码一致的条目 / 总条目；
   - **必填字段完整率** = 各类型 `REQUIRED` 字段中"渲染时提供且被解析器恢复"的字段槽 / 总字段槽（同时记录"渲染时提供率"，以区分数据缺口与解析丢失）；
   - **缺陷分布** = 问题按 level / field / message 计数；
   - **解析字段恢复率** = 对渲染时确实提供的字段，解析值（归一化后）与提供值一致的比率。
5. **30 条格式漂移**：取 5 条满足"≥4 位不同作者 + 有卷期页 + 有 DOI"的真实 `[J]` 条目为基线，每条的 6 类漂移各构造 1 条（共 30 条）：
   缺卷期 / 页码用 ASCII 连字符（`1-5`，规范 `1–5`）/ 4 名作者不用「等」/ 缺 DOI / 卷期互换 / 期刊条目标成 `[D]`。
   **检出判定用"差分法"**：只统计相对该基线条目**新增**的问题（基线本身的问题不计），并按预期规则分为
   - `strict`：预期字段/规则的提示确实出现；
   - `indirect`：出现了新问题，但不是预期原因（例如 `[D]` 只报"缺少出版地"）；
   - `miss`：没有新增任何问题。

| 漂移类别 | 条数 | strict | indirect | miss | 说明 |
|---|---|---|---|---|---|

| 卷期互换 | 5 | **4** | 0 | **1** | 新增启发式：期号显著大于卷号 → warning；5 条里有 1 条卷/期数字都小，启发式无法判断 |
| **合计** | **30** | **29（96.7%）** | **0** | **1（3.3%）** |

> 与 2026-10-22 版本相比：strict 从 **15/30（50%）提升到 29/30（96.7%）**。提升分两部分：①新增 3 条规则（页码连接号提示、卷/期颠倒提示、`[D]` 类型码误标 error）带来 +10；②修正了 4 条漂移的**构造**——原来的基底是单页/文章号（如 `0810016`），把 en dash 换成连字符等于没改，现在为这类基底构造同宽度的两页区间再替换连接号，漂移才可观测（+4）。
> 诚实说明：这 6 类漂移是 E4 自己构造的，规则是看到漂移类别后补的，因此 29/30 是**规则回归指标**，不是"真实世界错误检出率"的上界；真实论文里还有大量规则未覆盖的错误类型（见 1.6）。

逐条明细（id / 类别 / 判定 / 触发的问题）在 `e4_format.json` 的 `drift_cases` 中，每条都保留了渲染串、解析结果、全部问题与"新增问题"。

### 1.5 结论

- 规则引擎的**"识别与字段完备性"能力可靠**：类型码 100%，`[J]` 必填字段 98.4%（余下是上游缺数据），卷期页/DOI 的解析恢复率 100%。
- 规则引擎的**"缺陷检出"能力在已知的 6 类漂移上达到 29/30（96.7%）**：缺字段类、作者数量类、类型码误标、页码连接号均可严格检出；唯一漏检是"卷/期数字都较小"的互换（需要元数据才能判断），已在报告里如实保留 miss。
- 因此**不能**把"格式检查未发现问题"表述为"格式没问题"。建议文案改为"未发现本规则集覆盖的问题"，并在答辩中把格式层定位为"完备性检查 + 有边界的规则检查"。
- 附带收获：首跑发现的标点规则反向误报（100/100 条标准写法被判错、合规分上限 88）是真实的规则缺陷，当日已修复；修复后 clean 率从 0% 回到 62%（新增作者不完整提示属于保守 warning，不是 error）。这说明 E4 这类"真实文献回灌"实验对规则回归是有效的。

### 1.6 局限

1. 100 条样本的"渲染器"和"解析器"同属本项目，渲染风格（en dash、`等`、`[J]` 紧跟题名）可能与真实投稿有系统性差异；结论适用于"本项目渲染风格下的规则回归"，不外推到所有中文期刊。
2. `[C]` 组为 0：OpenAlex `language:zh` 的 15 条 conference-paper 全是英文题名，不满足中文题名条件；类型码结论只覆盖 J/M。
3. `[M]` 只有 5 条，比例类数字（75%）只有计数意义。
4. 漂移是**程序化构造**的 5×6=30 条，不是从真实论文里采的错例；"检出率"是规则层能力的下界估计，不是真实世界错误率。
5. 差分检出法会忽略"漂移后问题恰好与基线相同"的情况（本次没有发生，已逐条检查）。
6. 实验期间 `gbt7714.py`、`reference_parser.py` 被更新；主表是 22:30 复跑（修复后、最新解析器）的结果，指标与 22:23 那次逐字节一致，`code_snapshot` 已记录。
7. 2026-10-23 规则更新：新增 3 条规则（页码连接号提示、卷/期颠倒提示、`[D]` 类型码误标 error），并修正 4 条单页基底的漂移构造（原构造不可观测）；strict 由 15/30 升到 29/30。该提升依赖 E4 自己的构造口径，是**规则回归指标**，不是真实世界错误检出率。

## 2. E5：CiteBench-CN 上的检索与延迟统计

### 2.1 目的

把主榜的 macro-F1 拆成"系统到底靠什么工作"的可解释统计：DOI 锚点命中多少、无 DOI 时题名回退是否可靠、字段比对触发比例、单条核验要多久、外部请求失败多少、以及跑一遍到底花多少次请求。

### 2.2 方法

1. 对 CiteBench-CN 250 条逐条执行 `parse_reference` + `metadata_verify.verify_reference`（与产品完全同一路径），**单线程顺序执行**以测延迟。
2. **缓存口径**：把 `metadata_verify._cache_path` 包一层 overlay——命中 `data/citebench_cn/cache/` 就直接读，未命中才写到 `data/experiments/cache_e5/`（**基准目录只读，不被改写**）。
3. **计数**：代理 `metadata_verify.requests`，统计真实 HTTP 请求、状态码、按域名的成功/失败；包装 `_field_mismatches` 统计字段比对触发次数；包装 `_cached_json/_cached_text` 统计 API 查询与缓存命中。
4. **延迟两口径**：
   - **warm**：缓存命中（复跑/演示场景），250 条全量；
   - **cold**：绕过缓存（首次联网场景），固定 seed 抽 12 条（6 条有 DOI、6 条无 DOI），原始结果存档 `data/experiments/e5_cold_sample.json`，复跑默认复用、不重复请求。
5. 失败率拆两种：**非 200 率**（含 DOI 404 这类"业务负结果"）与 **基础设施失败率**（429/5xx/超时，不含 404）。

|---|---|
| 数据集 | CiteBench-CN 250 条（100/75/75） |

| 冷启动样本 | 12 条（固定 seed，6 有 DOI / 6 无 DOI） |

| DOI 网络错误（error） | 4 / 175 | 2.3% |

> 4 条 error 不是本次新失败：CiteBench-CN 的既有缓存里本来就有 9 个 `DOI_STATUS=error`（评估期瞬时网络失败被写入缓存），其中 4 条落在本次 250 条上，故计为 `Unknown`（主榜把它们并入 Major）。这属于"负结果被缓存放大"的可复现性风险，见 2.5 第 2 条。

| └ OpenAlex | 38（37×404，1×429） | 12（6×429，2×404，4×200） |
| 非 200 合计 | 80（79×404 + 1×429） | 12（6×404 + 6×429） |
| 基础设施失败（429） | 1 / 80 = 1.25% | **6 / 26 = 23.1%** |

- **warm 复跑仍有 80 次请求**：37 条虚构 DOI 各 2 次（Crossref + OpenAlex 404）≈ 74 次，另有少数"Crossref 未注册、但 OpenAlex 能解析"的真实 DOI（其 Crossref 404 同样不被缓存）≈ 6 次。根因是 `_cached_json` **不缓存非 200 响应**，而 `lookup_doi_status` 又先调 `lookup_doi` 才查 `DOI_STATUS` 缓存，所以 404 每次都要重打。
- 本实验一次运行 **106 次请求**（首跑）／**80 次**（复用冷启动缓存后），均 ≤ 命题的 150 次上限；写入 JSON 的 `external_requests` 有逐项计数。
- 冷启动样本 6 次 429 出现在 22:16 前后，随后（22:22）OpenAlex 明确返回"当日免费额度已用尽（$0 remaining，UTC 0 点重置）"，所以这 6 次更可能是**当日额度耗尽**而非单纯限速；E7 的检索因此主要落在 Crossref。

**（f）判定分布自检**

`Exact 108 / Minor 67 / Major 71 / Unknown 4`，把 `Unknown→Major` 后与主榜混淆矩阵 `[[100,0,0],[8,67,0],[0,0,75]]` 完全一致——说明统计管线没有改变系统行为。

### 2.5 结论

1. **DOI 锚点是可靠的**：真实 DOI 138/138 全部解析成功；DOI 锚点覆盖 70% 的样本（175/250）。
2. **题名回退可用**：无 DOI 时 100% 能召回候选，69.3% 能匹配到题名（该子集真实文献占比正是 69.3%），对虚构题名 0 误判。
3. **字段比对覆盖 76%** 的条目；剩下 24% 是"没有候选/提前判 Major"，属预期。
4. **延迟必须分口径说**：缓存命中 7.2 ms/条；首次联网约 1.54 s/条（12 条样本）。只报 7 ms 会显著低估真实体验，只报 1.5 s 又不反映演示条件。
5. **可优化点（已量化）**：404 负结果没有缓存，导致每轮复跑多出约 74 次请求，并把这些条目的延迟从毫秒级拉到 ~1.3 s。建议对 404 做负缓存（短 TTL），或在 `lookup_doi_status` 里先查 `DOI_STATUS` 再 `lookup_doi`。

### 2.6 局限

1. **warm 不是真实首次体验**：它是"缓存已就绪"的复跑/演示条件；首次联网的 12 条冷样本只是量级估计（n=12，且部分请求被 429 快速失败，可能低估真实冷延迟）。
2. **4 条 DOI error 来自既有缓存**：CiteBench-CN 缓存中 9 个 `DOI_STATUS=error` 是评估期瞬时失败的产物，被永久缓存；本次没有重试它们（否则会产生新请求）。这既是统计口径问题，也是产品可复现性风险。
3. **延迟在单线程、无 Web 层**下测量：不含上传、解析 PDF、排队、前端轮询/渲染；E7 的端到端数字包含这些。
4. **请求计数依赖代理注入**：只统计 `metadata_verify` 发出的 GET；`doi.org`/`api.crossref.org` 的其他调用（如 E7 人工核对）不计入 E5。
5. 冷启动样本的 429 与当日额度耗尽混在一起，无法完全区分"限速"与"额度用尽"。
6. 代码在 E5 首跑后更新过（`metadata_verify.py` 22:19、`reference_parser.py` 22:24）：warm 主表是 22:24 复跑结果；冷样本是 22:16 首跑结果。

## 3. E7：Web 工作台内部可用性自测

### 3.1 目的与口径

走一遍真实使用路径，回答：**从打开工作台到拿到报告要几步、多久；报告是否可读/可导出；哪些交互会卡住人**。

> **口径（必须照抄）**：这是**内部可用性自测**（internal usability self-test），由实验执行者单人完成，**没有招募任何用户，不是用户实测，也不是受试者调研**。步数按前端交互步骤计，耗时为本机单次实测，不可外推为"用户体验"结论。

### 3.2 方法

1. **被测对象**：本地 `uvicorn web.app:app --host 127.0.0.1 --port 8011`（v0.3.0），运行期开启 `DEEPSEEK_API_KEY` 以走通"引用支持度"路径；测试结束已关闭进程（端口 8011 已确认无监听）。
2. **驱动方式**：用 HTTP 客户端复现前端的调用序列——`GET /` → `POST /api/analyze`（multipart 文件）→ 轮询 `GET /api/jobs/{id}` → `GET /report/{id}` → `GET /api/report/{id}` → `GET /api/report/{id}/export?format=html|md|json`。**没有做真实浏览器点击/渲染计时**。
3. **步数定义**：记录 8 个步骤（打开首页、选择文件、开始体检、进入报告页轮询、分析完成、阅读报告、读取报告 JSON、导出）；其中**用户主动操作 3 步**（选择文件、点「开始体检」、导出），其余为系统自动动作。
4. **三篇文档**：
   - `web/static/samples/sample_paper.txt`（项目自带示例，12 条，含 2 条年份漂移 + 2 条虚构）；
   - `paper_b_lung_cancer_screening_2018.txt`、`paper_c_lung_cancer_projection_2010.txt`：两篇**公开可获取的真实中文论文节选**（Europe PMC 全文 XML，**CC BY**，中国肺癌杂志），内容为"标题 + 中文摘要 + 含引注的正文段落 + 文献表中可渲染的前若干条（按 GB/T 风格重排，字段全部来自原文）"。出处、DOI、PMCID、许可写在 `data/experiments/papers/SOURCES.json`。
5. **附加契约探针**（不额外造任务）：`.docx` 上传、旧版 `.doc` 上传、`support_max=0` 是否被遵守、未知任务 id 的页面、前端轮询间隔。
6. **人工核对 12 条**：取示例论文的 12 条参考文献，逐条用 **Crossref 元数据 + doi.org handle 存在性**比对题名/年/作者/来源/卷期页，人工判 Exact/Minor/Major；计时由脚本在第一次检索前写入 `started_at`、在判定结果落盘时写 `finished_at`，**含检索 + 阅读 + 判断**。

### 3.3 数据与结果

**（a）端到端**

| 文档 | 参考文献 | 端到端耗时 | 记录步骤 | 主动操作 | 判定（Exact/Minor/Major/Unknown） | 支持度（support/partial/…/未检测） | 导出 |
|---|---|---|---|---|---|---|---|
| `sample_paper.txt` | 12 | **4.13 s** | 8 | 3 | 8 / 2 / 2 / 0 | 8 / 0 / 0 / 2 / 2 | html/md/json 均 200 |
| `paper_b`（肺癌筛查指南 2018 节选） | 12 | **28.91 s** | 8 | 3 | 0 / 11 / 1 / 0 | 1 / 2 / 0 / 1 / 8 | 均 200 |
| `paper_c`（肺癌负担 2010 节选） | 9 | **13.71 s** | 8 | 3 | 0 / 2 / 7 / 0 | 0 / 0 / 0 / 1 / 8 | 均 200 |

- `sample_paper` 的 8/2/2 与示例设计一致（2 条年份漂移 → Minor，2 条虚构 DOI/题名 → Major），可作为"演示基线"。
- `paper_b` 的 11 条 Minor 主要来自**样张重排与 Crossref 记录的展示差异**（期刊缩写 `Int J Cancer` vs 全称、在线优先年份、作者缩写等），不是工具把真论文判错；`paper_c` 的 7 条 Major 主要因为该文引用多为 1980–2008 年的中文报告/汇编（无 DOI、不在 Crossref），且运行期 OpenAlex 已 429，题名回退只剩 Crossref 可用。
- **这两篇的判定不应被当作准确率指标**（准确率看 E1–E5）；它们只服务"可用性路径是否走得通"。

**（b）人工核对（同一 12 条）**

| 指标 | 值 |
|---|---|
| 条数 | 12 |
| 人工总耗时 | **30.2 s**（计时区间：第二次批量取数 → 判定落盘；其中取数 3.3 s） |
| 每条平均 | **2.5 s** |
| 与工具判定一致 | **11 / 12 = 91.7%** |
| 不一致条目 | 第 5 条：工具判 Exact，人工判 **Minor** |

不一致原因：该条 DOI 由 ChinaDOI 注册（Crossref 404、doi.org 句柄存在），条目的"来源"被著录为 `DOAJ (DOAJ: Directory of Open Access Journals)`（索引库而非期刊），且缺卷/期/页码；人工按题名在期刊站点核对到该文实为《水科学进展》2017, 28(5)。工具因为**上游 OpenAlex 记录本身就把来源写成 DOAJ**，来源比对通过，于是漏掉了这个来源错误。这是一个真实的"上游元数据噪声 → 工具漏检"案例，也说明多源核验并不能消除上游错误。

> **人工耗时的诚实说明**：执行者是 AI 助手（本次实验的工程师），阅读与判断速度与人类不同；12 条一次性批量检索也减少了人工切换成本。**30.2 s / 2.5 s per ref 只能作为同场景量级参考，不能代表真实用户耗时**；要得到用户耗时必须另做有受试者的计时研究。计时方法：Python `datetime`，`started_at` 在第一次检索前记录，`finished_at` 在判定结果落盘时记录，包含检索、阅读与判断。

**（c）体验问题（≥3）**

| # | 严重度 | 问题 | 证据 | 影响 |
|---|---|---|---|---|
| UX1 | 中 | 旧版 `.doc` 上传被接受后才异步失败 | `POST /api/analyze(.doc)` → 202，任务随后 `error: 暂不支持旧版 .doc 格式…`；`app.py` 允许 `.doc`，`pdf_extract.extract_text` 明确拒绝 | 用户要等任务跑起来才看到提示；失败任务留在最近列表，需重来 |
| UX2 | 中 | 进度粒度粗、无法取消、完成后整页刷新 | 前端固定 1.4 s 轮询（`report.js pollJob`）；本次 3 篇分别记录了多次进度跳变；无取消按钮；`location.reload()` | 长任务（28.9 s）期间无法干预；大文件上传也没有上传进度 |
| UX3 | 低 | 未知任务 id 返回 JSON 错误而非友好页面 | `GET /report/doesnotexist` → 404 `{"detail":"job not found"}` | 从旧链接/被清理任务进入时看到裸 JSON |
| UX4 | 中 | 「未检出问题」的呈现强于规则层真实能力 | 报告页对无 issue 条目标注「新国标字段检查未发现问题」；E4 显示 30 条漂移中 10 条无提示 | 用户会把"规则没查到"当成"格式没问题"，过度信任合规结论 |
| UX5（补充观察，未写入 JSON） | 低 | 导出/报告里的"输入文件名"变成 job id | 本次任务的 `report.input` 为 `1d0919a40d98.txt`、`13e2837c9597.txt`（上传后落盘改名为 `{job_id}.{ext}`，`pipeline` 用文件路径名当来源） | 用户下载/归档报告后难以对应原稿；报告页标题用的是 `job.filename`，与导出内容不一致 |

已核对**不是问题**的两项（v0.3.0 已修复）：`.docx` 上传返回 202 并能解析；`support_max=0` 被遵守（`support_meta.cap=0, judged=0, skipped_by_cap=4`）。

**（d）契约探针原始结果**

### 3.4 结论

- **主路径走得通**：3 篇文档都完成了"上传 → 核验 → 报告 → 三种格式导出"，无 500；示例论文 4.1 s、两篇真实论文 28.9 s / 13.7 s。
- **交互成本低但反馈粗**：用户只需 3 次主动操作；代价是进度不可控（1.4 s 轮询、无取消、完成整页刷新），长任务体感差。
- **报告的可信度表述需要收紧**：格式检查的"未发现问题"应改为"未发现本规则集覆盖的问题"（与 E4 的 50% 漏检呼应）。
- **人工/机器一致率 11/12**，唯一分歧暴露了"上游来源错误 → 工具漏检"的真实风险；这类问题应通过"来源黑名单 + 多源交叉"缓解，而不是继续加规则。

### 3.5 局限

1. **不是用户研究**：单一执行者、n=1 次运行、无受试者、无 SUS/问卷；执行者是 AI 助手，人工耗时不可外推。
2. **HTTP 驱动而非浏览器**：步数按前端交互步骤折算，未测真实渲染、点击、滚动、下载耗时；页面截图/视觉问题未评估。
3. **两篇"真实论文"是节选 + 重排**：正文只保留含引注且引用编号 ≤12 的段落，文献表取可渲染的前 9–12 条并按 GB/T 风格重排；因此 `paper_b/paper_c` 的判定分布不能当准确率。
4. **运行期外部源降级**：OpenAlex 当日额度在 22:22 前后耗尽（429），无 DOI 的旧文献只能靠 Crossref 题名检索，`paper_c` 的 7 条 Major 与此强相关；这会影响耗时与判定，但不影响"交互路径是否可用"的结论。
5. **支持度判定仅 4 条**（`paper_b`）与 1 条（`paper_c`）触发，样本太小，不能据此评价 support judge 的质量（质量看 ClaimSupport-CN 0.7951/0.810）。
6. 任务 id 作为报告标题的问题（UX5）是文本观察，未做用户验证。
